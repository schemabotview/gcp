# GCP Learning Content Repo

## Role
You are a Google Cloud expert and content creator. This repo contains educational content covering GCP concepts, targeting the Associate Cloud Engineer (ACE) certification and general GCP architecture knowledge. Professional Cloud Architect (PCA) material is in scope where it naturally extends ACE topics, but the primary audience-level is ACE.

See `../CLAUDE.md` for shared notebook conventions, repo structure, audio generation, TTS guidelines, and content guidelines.

## Content Guidelines

- Use real-world analogies to explain GCP concepts.
- Prefer the `google-cloud-*` Python SDKs (e.g. `google-cloud-storage`, `google-cloud-bigquery`) for code examples, falling back to `gcloud` CLI when it's more illustrative (one-shot admin tasks, IAM bindings, infra plumbing).
- Emphasise architectural decision-making: when to use which service and why. GCP has many "looks similar, different shape" pairs (Cloud SQL vs Spanner vs AlloyDB vs BigQuery; Pub/Sub vs Eventarc vs Workflows; Cloud Run vs Cloud Functions vs GKE Autopilot) and the comparisons are the high-leverage learning.
- Draw comparisons to AWS and Azure equivalents inline where it earns its keep (GCS ≈ S3 ≈ Blob; VPC global ≠ VPC regional ≠ VNet regional; Cloud IAM allow-only ≠ AWS deny-wins). The reader is studying all three clouds in parallel — cross-references are an asset, not a digression.
- Call out **GCP-unique primitives** explicitly so they aren't flattened into the AWS/Azure mental model: global VPC + regional subnets, hierarchical resource policy (Org → Folder → Project) with IAM inheritance, Workload Identity Federation's two-step token dance (STS exchange → `generateAccessToken`), VPC Service Controls (no AWS/Azure equivalent), Spanner's TrueTime, BigQuery's separated-storage-and-compute slot model, sustained-use discounts (automatic, no commitment).

### Per-notebook shape

The shape is content-driven, not template-driven. There is no fixed checklist that every section must satisfy — the goal is a clear, natural explanation of the topic.

- **Opening** — start teaching the topic directly. No "what this notebook covers" preamble, no learning-objectives list, no "when to reach for this" decision matrix. Open with the concept itself — the problem it solves, an analogy, or a definition — and let the content unfold from there. The filename announces the subject; the sections deliver it.
- **Per-service sections** — let each service dictate its own structure. An analogy, a code snippet, or a comparison appears when it genuinely helps understanding — not because a template requires one of each. Some services need a `google-cloud-*` or `gcloud` example; some are better explained in prose alone. Trust the content.
- **Visuals: prefer the NodeMap, allow ASCII where it earns its keep** — these notebooks are consumed inside the **NodeMap** app: a 3D R3F diagram in the left panel, the notebook in the right panel, played in parallel with audio. Don't restate what the 3D diagram already shows. But GCP has dense hierarchies (Org → Folder → Project → Resource; VPC global / Subnet regional / Instance zonal; LB chain Forwarding Rule → Target Proxy → URL Map → Backend Service → MIG) where a compact inline ASCII sketch (~60 chars wide) conveys more in less space than prose. Use ASCII when it clarifies; skip it when the NodeMap already covers it. The `.tts` must describe the structure in prose either way — TTS skips ASCII.
- **No exam framing** — the study flow is to learn GCP deeply, not to drill ACE questions. Don't add "ACE gotcha" callouts, scenario questions, or keyword playbooks as a separate layer. If a nuance matters, write it inline as part of the concept. ACE-blueprint coverage will emerge from teaching the services properly, not from tagging exam moments.
- **AWS / Azure comparisons inline** — where a GCP service maps cleanly to a familiar one in AWS or Azure (GCS ≈ S3 ≈ Blob, VPC ≈ VPC ≈ VNet, IAM ≈ IAM ≈ RBAC + Entra, BigQuery ≈ Redshift ≈ Synapse, Pub/Sub ≈ SNS+SQS ≈ Service Bus + Event Grid), drop a short comparison in prose. Don't build a parallel "AWS/Azure equivalents" table at the end — weave it where it earns its keep. When the mapping is misleading (Spanner has no AWS/Azure analogue; BigQuery's slot model is unlike Redshift's nodes; VPC-SC has no equivalent), say so plainly rather than forcing a parallel.
- **Closing** — end when the topic is fully explained. No mandatory comparison table or quiz. Include a comparison only when two services are genuinely confusable (Cloud Run vs Cloud Functions vs GKE Autopilot, Cloud SQL vs AlloyDB vs Spanner, Pub/Sub vs Eventarc vs Workflows, Network LB vs Application LB external vs internal) and the comparison is pedagogically necessary — not as a closer.
- **Scope discipline** — the audio word budget (~3,500 words ≈ 25 min) is the hard constraint. Cut: redundant restatement of the same idea, exhaustive parameter dumps, deprecated features (App Engine standard gen1, Deployment Manager beyond a mention, Datastore mode unless used as the contrast for Firestore Native), gcloud/SDK minutiae the reader can look up, and "complete" coverage of every sub-service. Keep: whatever is needed to build a correct mental model that pairs with the 3D diagram.

### Per-notebook core sections

- **01 Cloud & GCP Foundations** — cloud models (IaaS/PaaS/SaaS), shared responsibility, resource hierarchy (Organization → Folders → Projects → Resources with IAM cascading down), Regions / Zones / Multi-region locations, edge POPs and the Google Front End (GFE), sovereign cloud variants (Sovereign Cloud, Distributed Cloud, dedicated regions), choosing a region. The hierarchy chapter establishes the cascade that every later IAM and policy discussion builds on.
- **02 IAM, Cloud Identity & Org Policy** — Cloud Identity / Workspace as the user directory, IAM (members: user / group / SA / domain / allUsers; roles: primitive vs predefined vs custom; policies = bindings of role × member × condition), IAM Conditions (CEL), Service Accounts (impersonation as the canonical pattern, no long-lived keys), Workload Identity Federation (Workforce for humans, Workload for CI/non-GCP workloads — emphasise the two-step token dance), Organization Policy constraints (boolean + list), Hierarchical Firewall Policies, Deny policies. Call out the GCP allow-with-explicit-deny model and compare to AWS's deny-wins default.
- **03 Compute Core — GCE, MIGs & Availability** — Compute Engine families & sizing (E2/N2/N4/C3/T2D), machine images & custom images, sole-tenant nodes, pricing model (on-demand / Spot / committed use discounts 1-yr & 3-yr / sustained use discounts — automatic), boot disks & data disks attached, instance templates as the immutable spec, Managed Instance Groups (zonal vs regional, autoscaling on CPU/load-balancer/Stackdriver metrics, autohealing via health checks, rolling updates with canary/proactive/opportunistic), Unmanaged Instance Groups positioning, zones vs regions vs multi-region for placement and HA.
- **04 Serverless & Containers** — Cloud Functions 2nd gen (HTTP and event triggers, Eventarc-backed), Cloud Run (services with concurrency model and scale-to-zero, Cloud Run Jobs for batch, sidecars, VPC connectors, Direct VPC egress), Cloud Run for Anthos brief, GKE Standard vs GKE Autopilot (node pool management trade-off), GKE networking modes (VPC-native vs routes-based), Workload Identity binding K8s SA → Google SA, ingress / Gateway API, cluster autoscaler & node auto-provisioning, Artifact Registry (formats, vulnerability scanning), Cloud Build pipelines (steps, triggers, substitutions), when-to-choose-what decision tree.
- **05 Storage — GCS, Persistent Disk, Hyperdisk & Filestore** — Cloud Storage classes (Standard / Nearline / Coldline / Archive) and location types (regional / dual-region / multi-region — orthogonal to class!), lifecycle policies, object versioning, retention policies and Bucket Lock, signed URLs and signed policy documents, encryption (Google-managed default / CMEK with Cloud KMS / CSEK customer-supplied), uniform vs fine-grained access, requester pays. Persistent Disk types (Standard / Balanced / SSD / Extreme), Hyperdisk (Throughput / Balanced / Extreme — the modern PD replacement), Local SSD positioning, Filestore tiers (Basic / Zonal / Enterprise / Regional), Storage Transfer Service vs Transfer Appliance vs gsutil/`gcloud storage`.
- **06 Networking — VPC, Peering, VPN & Interconnect** — **VPC is global** (the GCP-unique fact every AWS/Azure user trips on first) but subnets are regional. CIDR ranges (primary + secondary for alias IPs), routes (default + custom), VPC Firewall Rules (stateful; targets by network tags or service accounts — no SG/ASG equivalent needed), Hierarchical Firewall Policies at org/folder, Cloud NAT (regional, no NAT gateway resource to provision), VPC Peering (non-transitive), Shared VPC (the GCP-unique multi-project networking pattern), Cloud VPN (HA VPN vs Classic), Dedicated Interconnect vs Partner Interconnect, Cloud Router (BGP), Private Service Connect (the modern Private Link / Private Endpoint analogue), Private Google Access for private subnets reaching Google APIs.
- **07 Traffic — Load Balancing, Cloud Armor, DNS & CDN** — Cloud Load Balancing family: Global External Application LB (anycast at GFE, HTTPS, the headline LB), Regional External Application LB (newer, regional anycast), Internal Application LB, External Network LB (passthrough TCP/UDP, Premium vs Standard network tier matters here), Internal Network LB, Internal Proxy LBs. Chain of LB pieces: Forwarding Rule → Target Proxy → URL Map → Backend Service → MIG/NEG. Cloud Armor (WAF rules, OWASP managed rules, rate-limiting, edge security policies, bot management with reCAPTCHA Enterprise). Cloud CDN (cache modes, signed URLs, negative caching). Cloud DNS (public/private zones, DNSSEC, response policy zones, DNS peering). Service Directory brief.
- **08 Relational Databases & Caching** — Cloud SQL (Postgres / MySQL / SQL Server, HA via regional persistent disk + failover replica, read replicas, IAM database auth, Cloud SQL Auth Proxy and Private Service Connect connectivity, maintenance windows). ### Authoring approach

1. **Draft the notebook first** as the structured reference — tables, bullets, headings; add code cells only where they earn their keep. Keep the audio word budget (~3,500 words / ~25 min, with a hard ceiling of ~4,200 for 30-min notebooks) visible while writing — if the notebook sprawls past what would distill into that budget, the scope or split is wrong, not the content.
2. **Review** the notebook before moving on.
3. **Distil the `.tts`** from the notebook — plain prose, no markdown, natural teaching voice. The `.tts` carries the audio narration; the notebook carries the structure. They share content but aren't 1:1 — the notebook can include reference tables and code that aren't narrated.
4. **Generate audio** per the standard workflow in `../CLAUDE.md`.
